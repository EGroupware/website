PHP2Shell and Our Strategy

General · October 27, 2026

On 21 October 2026 the PHP project disclosed two critical security vulnerabilities. What EGroupware did, when the systems were patched and what to check on your own installation.

CVE-2026-109618 and CVE-2026-109619 · Measures taken by EGroupware GmbH · As of 27 October 2026

Key points at a glance

Update 27 October 2026: Since 26 October 2026, the vulnerabilities have been actively exploited in attacks, according to the EU Agency for Cyber­security (ENISA) and the US agency CISA. We are not aware of any case affecting EGroupware installations so far. Please make sure that your installation is up to date.
On 21 October 2026, the PHP project published two critical vulnerabilities in PHP (CVSS 9.2). They
may allow attackers to execute code on the server without logging in.
We applied mitigations on the same day and released the fixed PHP version 8.5.12 that evening:
EGroupware 26.10.20261021 and EGroupware 23.1.20261021.

EGroupware Cloud

All systems have been running PHP 8.5.12 since the evening of 21 October
2026. No action is required on your part.

Self-hosted installations

Standard installations received the update automatically during the night
of 21 to 22 October 2026. Please check that PHP 8.5.12 is in use (see section 6).
Our review found no indication that the vulnerabilities were exploited on EGroupware installations.

1. The vulnerabilities

The PHP project announced the publication on 20 October 2026. Because of a leak, it was brought forward by
one day: the details and the fixed versions became public on 21 October 2026 between approx. 15:40 and
16:00 CEST (first media reports from 15:42, official PHP announcement at 16:00). According to PHP, all PHP
installations that handle web requests are affected, including PHP-⁠FPM, which EGroupware also uses. An
attack is possible without logging in and takes place before any application code runs. It therefore does not
matter which PHP functions EGroupware itself uses.
Vulnerability Description according to the PHP advisory
CVE-2026-109618
“RCE via OOM
corruption”
If PHP runs out of memory during a request, processing can abort while internal request data
is only partially initialised. The subsequent cleanup then treats this invalid data as valid.
CVE-2026-109619
“RCE via stale
global state”
Internal data of a request can persist even though its memory has already been freed. A later
request handled by the same PHP process can then use this stale data.
The vulnerabilities are fixed in PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35. According to PHP, there is no complete
mitigation without updating.

2. Why PHP-⁠FPM is affected and what we changed

EGroupware runs on PHP-⁠FPM. A pool of continuously running PHP processes (“workers”) handles many
requests one after another. This is fast, but it also means that whatever one request leaves behind in a worker
can affect the next request in the same worker. This is exactly what the vulnerabilities exploit.
CVE-2026-109619: An attacker sends a crafted request that leaves stale data in the worker. If the next
request is handled by the same worker, this can lead to code execution. Confirmed attack paths use the
PHP “upload progress” feature ( session.upload_progress ) and, on PHP 8.5, additionally error backtraces
for fatal errors ( fatal_error_backtraces ).
CVE-2026-109618: An attacker deliberately pushes PHP to the memory limit of a request ( memory_limit )
so that processing aborts at a critical point.
Until the fixed PHP version was available, we therefore applied the mitigations recommended by the PHP
project in the PHP-⁠FPM configuration.
Upload sizes ( post_max_size , upload_max_filesize ) are already limited in EGroupware. We did not lower
them further, as the PHP project mentions as an additional option, because larger uploads in the file manager
would then no longer be possible.

To make the update available quickly, we switched the base image of our Docker containers to the official Alpine Linux based PHP image. PHP 8.5.12 was available there earlier than in the Ubuntu packages we had been using.

4. Results of our review

  • We reviewed the EGroupware Cloud logs for the period from 20 October 2026 until shortly after all mitigations were applied on 21 October 2026 and found no anomalies. At that time, the vulnerabilities were not known to be actively exploited. Since 26 October 2026, ENISA and CISA have listed them as actively exploited. We are not aware of any attacks on EGroupware instances.
  • The attack path of CVE-2026-109619 requires two requests to be handled one after another by the same PHP process. In the EGroupware Cloud, requests are distributed across several PHP-⁠FPM servers. Together with the early first mitigation, we consider the likelihood of a successful exploitation to be very low.
  • Push server: The EGroupware push server is also based on PHP (Swoole). We tested whether the attack path via upload progress can be exploited there. The result was negative. We nevertheless applied the mitigation as a precaution and updated the push server on 22 October 2026 to a version with the fixed PHP 8.4.27.
  • Collabora Online: On 21 October 2026, we checked whether Collabora Online and the Collabora controller (COOL Controller) used in the cloud are affected. Neither uses PHP, so neither is affected. Collabora accesses your documents through EGroupware, which is covered by the mitigations and the PHP update.

5. Additional protection beyond the update

We kept two of the mitigations in place after the PHP update. They turn off PHP features that EGroupware does not need at all: the upload progress display and detailed error reports for fatal errors. Nothing changes for you; EGroupware works as usual. For attackers, however, there are fewer ways in: what is switched off cannot be exploited, even by future vulnerabilities.
This has already paid off: on 23 October 2026, the PHP project reported another vulnerability that has not yet been fixed (CVE-2026-115560). As protection, PHP recommends exactly this: turning off upload progress. The EGroupware Cloud and installations using our current images were therefore already protected before the vulnerability became known. PHP will deliver the final fix with its next regular update, which we will include in our images as usual.

6. What you need to do

EGroupware Cloud

Nothing. All systems are up to date.

Self-hosted installation (Docker, DEB/RPM packages)

If automatic updates (Watch­tower) are enabled, the update was applied during the night of 21 to 22 October 2026. If they are disabled or you have pinned a fixed version, please update manually:

cd /etc/egroupware-docker
docker compose pull && docker compose up -d && docker logs -f egroupware
# Press Ctrl-C once "NOTICE: fpm is running, pid 1" appears

Check: Under Admin → PHP information, PHP 8.5.12 (or newer) must be shown.

Univention / Nubus

Univention published the update with PHP 8.5.12 on 23 October 2026 at 15:12. Please install it via the Univention App Center if you have not already done so.

If you installed the update manually before­hand, following our instructions in the forum, your installation is already up to date. You can install future updates via the App Center as usual.

EGroupware 23.1 and older versions

EGroupware 23.1 is no longer supported. Because of the severity of the vulnerabilities, we are providing release 23.1.20261021 as an exception and without extending support. It is the final update for 23.1. It contains PHP 8.5.12 and most, but not all, security updates of EGroupware 26. The security notice within EGroupware 23.1 therefore remains active. Please update to EGroupware 26 soon. There are no more updates for versions before 23.1.
